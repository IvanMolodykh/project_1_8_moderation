# Backend — система модерации статей

Серверная часть платформы управления модерацией пользовательского контента.
ASP.NET Core Web API, .NET 8, PostgreSQL.

---

## 1. Описание проекта

### Задача

Платформы с пользовательским контентом (новостные площадки, блоги, форумы,
образовательные сервисы) не справляются с ручной проверкой материалов: растёт
нагрузка на сотрудников, замедляется публикация, появляется нежелательный контент.

Проект — универсальный сервис модерации, к которому подключаются разные платформы,
чтобы не разрабатывать собственный процесс проверки с нуля. Система принимает
материалы на проверку, организует работу модераторов и отслеживает результат.

### Текущее состояние

Реализована **инфраструктурная часть** — фундамент, на который будет надстраиваться
бизнес-домен:

- подключение к PostgreSQL с пулом соединений;
- конфигурация окружений dev / prod с валидацией при старте;
- базовый DI-контейнер с корректными временами жизни сервисов;
- репозиторий на сыром SQL как образец работы с базой;
- автоматическая инициализация схемы и health-check;
- Swagger и единый формат ошибок.

Бизнес-домен модерации (статьи, версии, история решений) **пока не реализован**.
Сущность `User` в текущей версии — затычка: она нужна, чтобы продемонстрировать
работу с базой и контейнером до появления реальной предметной области.

### Технологии

| Компонент | Версия |
|---|---|
| .NET | 8.0 |
| ASP.NET Core | 8.0 |
| PostgreSQL | 16 и выше (проверено на 18.6) |
| Npgsql | 8.0.9 |
| Swagger | Swashbuckle 6.6.2 |

## 2. Структура решения

```
backend/
├── Paper.Domain/           сущности и абстракции, ни от кого не зависит
├── Paper.Application/      сценарии, DTO, маппинг
├── Paper.Infrastructure/   работа с PostgreSQL, вся DI-регистрация
├── PaperAPI/               HTTP-слой и точка сборки зависимостей
├── Paper.slnx
├── Dockerfile
├── docker-compose.yml
└── .env.example
```

Направление зависимостей строго внутрь:

```
PaperAPI ──▶ Paper.Application  ──▶ Paper.Domain
         └─▶ Paper.Infrastructure ──▶ Paper.Domain
```

`Paper.Domain` не знает ни про Npgsql, ни про ASP.NET Core, ни про контейнер.
`Paper.Application` не знает, что база существует, — только про `IUserRepository`.

Решение лежит в формате `.slnx`:

```bash
dotnet build backend/Paper.slnx
```

## 3. Инструкция по запуску

### Требования

- Docker Desktop — для стенда одной командой
- .NET SDK 8.0 или выше (проверено на 10.0.401) — только если API запускается на машине, а не в контейнере
- PostgreSQL 16+ — только если база ставится программой, без Docker

### Способ 1: весь стенд одной командой

Из папки `backend`:

```bash
docker compose up --build -d --wait
```

Команда собирает API, поднимает PostgreSQL и веб-интерфейс базы. Первый запуск
дольше: скачиваются образы и собирается приложение. `--wait` завершится, когда
API и база станут `healthy`.

| Что проверить | Адрес |
|---|---|
| Swagger | http://localhost:5009/swagger |
| API и подключение к базе | http://localhost:5009/api/health |
| База в браузере (Adminer) | http://localhost:8081/?pgsql=&username=postgres&db=moderationdb |

Форма Adminer уже заполнена: система PostgreSQL, сервер `postgres`, пользователь
`postgres`, база `moderationdb`. Остаётся ввести пароль `postgres` и нажать Login.
Таблица `users` содержит трёх тестовых пользователей — те же данные отдаёт `GET /api/users`.

Та же база открывается из DBeaver, DataGrip или `psql`: хост `localhost`, порт
`5432`, база `moderationdb`, пользователь и пароль `postgres`.

Остановка: `docker compose down`. Вместе с данными: `docker compose down -v`.

Если порт `5432`, `5009` или `8081` занят, скопируйте `.env.example` в `.env`
и поменяйте `POSTGRES_PORT`, `API_PORT` или `ADMINER_PORT`.

### Способ 2: API на машине, база в Docker

```bash
cd backend
docker compose up -d postgres
dotnet run --project PaperAPI
```

Swagger: **http://localhost:5009/swagger**. Остановить API — `Ctrl+C`.

### Способ 3: локальный PostgreSQL

Установите PostgreSQL обычной программой, при установке задайте пароль `postgres`
и кодировку UTF-8. Затем создайте базу:

```bash
createdb -U postgres moderationdb
```

Приложение создаёт таблицы само при первом запуске, вручную ничего делать не нужно.
Дальше тот же `dotnet run --project PaperAPI`.

После старта локального API в консоли появятся строки:

```
PostgreSQL: localhost:5432/moderationdb (user=postgres, pool=0..10)
Схема готова: таблица users создана или уже существует
Now listening on: http://localhost:5009
```

### Конфигурация окружений

| Файл | Назначение |
|---|---|
| `PaperAPI/appsettings.json` | базовые значения, общие для всех сред |
| `PaperAPI/appsettings.Development.json` | разработка: подробные логи, автосоздание схемы, тестовые данные |
| `PaperAPI/appsettings.Production.json` | продакшен: увеличенный пул, `SslMode: VerifyFull`, схема не создаётся |

Секция `Database`:

| Ключ | Назначение |
|---|---|
| `Host`, `Port`, `Database`, `Username`, `Password` | параметры подключения |
| `ConnectionString` | готовая строка подключения; если задана — имеет приоритет над полями выше |
| `MaxPoolSize`, `MinPoolSize` | границы пула соединений |
| `ConnectionTimeoutSeconds` | сколько ждать установления соединения |
| `CommandTimeoutSeconds` | сколько ждать выполнения запроса |
| `SslMode` | `Disable` / `Allow` / `Prefer` / `Require` / `VerifyCA` / `VerifyFull` |
| `CreateSchemaOnStartup` | создавать таблицы при старте |
| `SeedData` | наполнять таблицу тестовыми данными |

**Fail-fast.** В продакшене значения намеренно пустые. Приложение падает при старте,
перечислив все недостающие поля, вместо того чтобы молча подключиться к `localhost`:

```
Секция "Database" в конфигурации заполнена некорректно:
  - Host пуст.
  - Password пуст.
  - MinPoolSize (50) больше MaxPoolSize (10).
```

Значения переопределяются переменными окружения (двойное подчёркивание — разделитель
уровней):

```bash
Database__Host=prod-db.cluster
Database__Password=...
Database__ConnectionString="Host=...;Database=...;SSL Mode=VerifyFull"
```

Пароль никогда не попадает в лог: для этого есть отдельный метод, маскирующий его
в строке подключения.

### Проверка работоспособности

```bash
curl http://localhost:5009/api/health
```

```json
{
  "status": "healthy",
  "database": "PostgreSQL 18.6",
  "target": "localhost:5432/moderationdb (user=postgres, pool=0..10)"
}
```

При недоступной базе приложение продолжает работать, Swagger остаётся доступен,
а эндпоинты отвечают `503` с указанием причины вместо `500` со стектрейсом.

## 4. Как устроено подключение к базе

```
DatabaseOptions          ← настройки из конфигурации, валидация при старте
        ↓
NpgsqlDataSource         ← Singleton, внутри пул физических соединений
        ↓
IDbConnectionFactory     ← Singleton, берёт соединение из пула
        ↓
IUserRepository          ← Scoped, весь SQL здесь
```

Ключевое решение — `NpgsqlDataSource` вместо нового соединения на каждый запрос.
Внутри него Npgsql держит пул и переиспользует физические соединения, поэтому:

- создавать его на каждый запрос бессмысленно дорого;
- создавать по копии на запрос — значит завести множество пулов и исчерпать лимит
  подключений к серверу;
- объект реализует `IDisposable`, и контейнер сам освобождает его при остановке
  приложения.

В репозитории соединение всегда освобождается через `await using`, поэтому при
любой ошибке оно возвращается в пул. Все значения передаются параметрами
(`@name`, `@email`), склейка строк не используется — SQL-инъекция невозможна.

## 5. Как устроен DI-контейнер

Все зависимости регистрируются в двух методах расширения, а не в `Program.cs`:

- `Paper.Application/DependencyInjection/ApplicationServiceCollectionExtensions.cs`
- `Paper.Infrastructure/DependencyInjection/InfrastructureServiceCollectionExtensions.cs`

`Program.cs` остаётся коротким и читаемым:

```csharp
builder.Services.AddApplication();
builder.Services.AddInfrastructure(builder.Configuration);
```

Это **composition root** — единственное место, где известны конкретные реализации.
Ни один компонент не создаёт зависимости вручную: только запрашивает их у контейнера
через конструктор.

### Времена жизни

| Сервис | Lifetime | Почему |
|---|---|---|
| `DatabaseOptions` | Singleton | неизменяемое значение из конфигурации |
| `NpgsqlDataSource` | **Singleton** | пул соединений общий на всё приложение |
| `IDbConnectionFactory` | Singleton | тонкая обёртка над пулом, состояния не хранит |
| `IAppLogger` | Singleton | реализация без состояния |
| `DatabaseInitializer` | Singleton | выполняется один раз при старте |
| `DatabaseHealthProbe` | Singleton | без состояния |
| `IUserRepository` | **Scoped** | один экземпляр на HTTP-запрос |
| `IUserService` | **Scoped** | один экземпляр на HTTP-запрос |

`Scoped` означает «один экземпляр на обработку одного запроса»: внутри запроса все
обращения к репозиторию дают один и тот же объект, а в следующем запросе — новый.

- `Singleton` был бы ошибкой: сервис пережил бы запрос и начал отдавать устаревшие данные;
- `Transient` тоже нежелателен: внутри одного запроса появилось бы несколько копий.

На Development включена проверка `ValidateScopes`, которая ловит две типичные ошибки:
Scoped-сервис, запрошенный из корневого контейнера, и Scoped-сервис, внедрённый
в Singleton («пойманная зависимость»).

## 6. API

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/api/health` | проверка приложения и БД: `200` или `503` |
| `GET` | `/api/users` | список пользователей |
| `GET` | `/api/users/count` | количество пользователей |
| `GET` | `/api/users/{id}` | пользователь по идентификатору, `404` если нет |
| `POST` | `/api/users` | создать пользователя: `201`, либо `400` с указанием поля |

Полная документация — Swagger UI по адресу `http://localhost:5009/swagger`.

## 7. Пользовательские сценарии

Сценарии определены техническим заданием проекта. В текущей версии реализована
инфраструктура, по которой эти сценарии будут строиться; сами сценарии модерации
пока в разработке.

### Управление статьями

| # | Сценарий | Результат |
|---|---|---|
| 1 | Пользователь создаёт статью с названием, содержанием и дополнительными данными | статья сохранена со статусом **«Черновик»** |
| 2 | Пользователь открывает список своих статей | видно название, статус и дату последнего изменения |
| 3 | Пользователь редактирует статью | для «Опубликованной» статус становится **«Черновик»**, нужна повторная модерация |
| 4 | Пользователь удаляет статью | статья исчезает из списка доступных материалов |

### Отправка на модерацию

| # | Сценарий | Результат |
|---|---|---|
| 5 | Пользователь отправляет подготовленную статью на проверку | статус **«На модерации»**, текущая версия сохранена, статья доступна модераторам |
| 6 | Попытка отправить неполную статью | отказ: обязательная информация не заполнена |

### Модерация

| # | Сценарий | Результат |
|---|---|---|
| 7 | Модератор открывает очередь | список ожидающих статей: название, автор, дата отправки, статус |
| 8 | Модератор открывает статью | видит полное содержание перед решением |
| 9 | Модератор открывает версии | дата отправки, автор правок, содержание на момент отправки, результат проверки, комментарий |
| 10 | Модератор **принимает** статью | статус **«Опубликована»**, статья доступна пользователям |
| 11 | Модератор **отклоняет** статью с комментарием | статус **«Отклонена»**, автор может внести правки и отправить заново |

### Публикация

| # | Сценарий | Результат |
|---|---|---|
| 12 | Пользователь просматривает опубликованные статьи | название, автор, содержание, дата публикации |
| 13 | Автор изменяет опубликованную статью | создаётся новая версия, статус становится **«Черновик»**, требуется повторная модерация |

### История модерации

| # | Сценарий | Результат |
|---|---|---|
| 14 | Просмотр истории своей статьи | даты отправки и решения, статус проверки, принявший решение, комментарий при отклонении |
| 15 | Просмотр истории модератором | то же самое по всем доступным статьям |

### Жизненный цикл статьи

Допустимые переходы между статусами:

```
Черновик ──────────▶ На модерации ──────────▶ Опубликована
                          │
                          └──────────────▶ Отклонена ──▶ Черновик

Опубликована ──(после изменения)──▶ Черновик
```

Инварианты:

- версия, отправленная на модерацию, не может быть изменена или удалена;
- история версий сохраняется независимо от текущего статуса;
- опубликованной может быть только статья, прошедшая модерацию;
- отклонённая статья не публикуется без повторной проверки;
- решения модераторов не изменяются и не удаляются.

## 8. Роли и зоны ответственности

### Роли в системе

| Роль | Возможности | Ограничения |
|---|---|---|
| **Автор** | создавать, редактировать и удалять свои статьи; отправлять их на модерацию; повторно отправлять после правок; просматривать опубликованные статьи и историю модерации своих материалов | видит только свои статьи; не может принимать решение по собственной статье |
| **Модератор** | просматривать очередь и содержание статей; сравнивать версии; принимать или отклонять с комментарием; видеть историю решений | не редактирует статьи; решение по статье фиксируется в истории и не изменяется |

Все действия выполняются авторизованными пользователями.

### Зоны ответственности команды

| Зона | Ответственный | Ответственность |
|---|---|---|
| Backend: инфраструктура | участник команды | подключение к БД, конфигурация окружений, DI-контейнер, health-check |
| Backend: домен и API | участник команды | сущности статей и версий, сценарии модерации, эндпоинты |
| Frontend | участник команды | интерфейс авторизации, формы, пользовательские сценарии |
| Тестирование | участник команды | автотесты, прогон в CI, проверка критериев приёмки |
| Документация | участник команды | README, техническая документация, описание ролей |

> Участников каждой зоны необходимо указать при оформлении отчётности.

## 10. Полезные команды

```bash
docker compose up --build -d --wait      # API, Swagger, PostgreSQL и Adminer
docker compose ps                        # статусы контейнеров
docker compose logs -f api               # логи API
docker compose up -d postgres            # только база, если API запускается через dotnet
docker compose down -v                   # удалить стенд вместе с данными
dotnet build backend/Paper.slnx          # собрать решение на машине
dotnet run --project backend/PaperAPI    # запустить API на машине
curl http://localhost:5009/api/health    # проверка работоспособности
```
